# Spec: real app foundation (profiles, tool sign-in, MCP servers, installers)

- **Status:** Accepted (owner request 2026-11-14: "installer, working sign-in of services, MCP and everything around it")
- **Implements:** `memory/features.json` F-002, F-003, F-004, F-010, F-011, the environment
  allowlist part of F-012, and the profile-scoped part of roadmap M10 (`docs/PLAN.md` §9).
- **Out of scope:** agent runs (F-006, F-020 to F-022), projects/workspaces, git service,
  knowledge layer, code signing with an Apple Developer ID, auto-update.

Evidence convention as in `docs/PLAN.md`: facts link to a source, design choices are *[opinion]*.

## 1. Goals

1. A user can install Vision from an installer (macOS `.dmg` with drag-to-Applications,
   Windows NSIS/MSI, Linux AppImage/deb) built by CI.
2. A user can create profiles (e.g. Work, Personal) that persist across restarts.
3. Per profile, a user can sign in to Claude Code, Codex, GitHub CLI, Google Cloud CLI,
   Azure CLI, AWS CLI and custom tools, each isolated by its own config directory, and see
   who is signed in.
4. Per profile, a user can add, edit, test and remove MCP servers (stdio and HTTP), see
   their tools, and push them into that profile's Claude Code config.
5. The UI shows real data from the core; no fake accounts.

## 2. Architecture

```
src/ (React)  ──invoke──▶  src-tauri (thin commands, state, spawn_blocking)
                               │
                               ▼
                        crates/vision-core  (no Tauri dependency, all logic, all tests)
   paths · db · profiles · env · process · tools · terminal · mcp · secrets · ipc types
```

Rules *[opinion]*:

- All logic lives in `vision-core` behind traits for every side effect, so tests never touch
  the real machine: `CommandRunner` (run a process with env, timeout, captured output),
  `TerminalLauncher` (open the system terminal), `SecretStore` (OS keychain), `McpProbe`
  (talk to an MCP server). `src-tauri` only wires real implementations and maps errors.
- Blocking work (process spawn, SQLite) never runs on the UI thread or the async runtime's
  core threads: Tauri commands are `async` and use `tauri::async_runtime::spawn_blocking`.
- No generic "run command", "read file" or "open URL" IPC (`docs/PLAN.md` §2.3). Every
  command takes ids; the core looks up what to run.
- Vision never reads, copies or stores a CLI's credentials (ADR-0004). It only sets config
  directory variables and runs the CLI's own status command.

### 2.1 Data root

`<data root>` = Tauri `app_local_data_dir()` (non-roaming); overridable with
`VISION_DATA_DIR` for development and tests (documented in `.env.example`).

```
<data root>/
├── app.db                      profiles, custom tools, app settings
├── backups/                    database copies taken before migrations
└── profiles/<profile-id>/      mode 0700 on Unix
    ├── profile.db              tool status cache, MCP servers
    └── tools/<tool-id>/        the tool's config home (owned by the CLI)
```

Profile ids are generated by the core (`p_` + 12 lowercase base32 chars from the OS RNG) and
are the only user-influenced path segment that is never user-typed. Tool ids are validated
`^[a-z][a-z0-9_-]{0,31}$`. No path is ever built from a display name.

### 2.2 Storage (F-003)

- SQLite through `rusqlite` with the `bundled` feature, WAL mode, `foreign_keys=ON`,
  `busy_timeout` set ([SQLite WAL](https://www.sqlite.org/wal.html)).
- Forward-only numbered migrations tracked in `PRAGMA user_version`. Before migrating an
  existing database from version N>0, checkpoint and copy it to `backups/`. Opening a
  database whose `user_version` is higher than the build knows fails with
  `ErrorCode::SchemaTooNew` and never modifies the file.
- One connection per database, guarded by a mutex; the core is the only writer.

### 2.3 Profiles (F-010)

`Profile { id, name, kind: work|personal|other, accent: iris|teal|amber|rose|green, created_at }`.

- Name: trimmed, 1 to 40 chars, no control characters, unique case-insensitively.
- Create makes the directory tree with user-only permissions, then the row; a failure rolls
  back both.
- Delete requires the exact profile name as confirmation, removes the row and the whole
  profile directory (this signs the profile out of every file-based tool login). On macOS,
  Claude Code keeps its login in the Keychain keyed to the config directory
  ([Claude Code authentication](https://code.claude.com/docs/en/authentication)), so the UI
  tells the user to sign out first if a tool is still signed in. The last profile can be deleted.
- The active profile id is an app setting persisted in `app.db`.

### 2.4 Tool registry and sign-in (F-011, F-012)

A registry entry:

```
ToolSpec {
  id, name, description, binary,                 // binary resolved on PATH, never a shell string
  install_url,                                   // official install page, https only
  config_env: [{ var, kind: dir|file, rel }],    // rel is relative to tools/<id>/
  extra_env: [{ var, value }],                   // fixed non-secret values
  login:  [argv...],                             // run in the system terminal
  logout: [argv...] | null,                      // run in the system terminal
  status: [argv...] | null,                      // run headless, timeout 20 s
  status_parser: claude|codex|gh|gcloud|azure|aws|exit_code,
  version: [argv...],                            // e.g. ["--version"]
  isolation: verified|unverified|none,
  builtin: bool
}
```

Built-in presets (sources in `docs/PLAN.md` §6.3; commands verified 2026-11-14):

| id | binary | config env | login | status | logout |
| --- | --- | --- | --- | --- | --- |
| `claude` | `claude` | `CLAUDE_CONFIG_DIR` | `auth login` | `auth status` (JSON; exit 0 signed in, 1 not; `authMethod`, `configDirectory`: [CLI reference](https://code.claude.com/docs/en/cli-reference.md)) | `auth logout` |
| `codex` | `codex` | `CODEX_HOME` | `login` | `login status` ([Codex auth](https://learn.chatgpt.com/docs/auth.md); exit codes undocumented, parse defensively) | `logout` |
| `gh` | `gh` | `GH_CONFIG_DIR` | `auth login --insecure-storage` (`docs/PLAN.md` §6.4) | `auth status --json hosts`, fall back to text `auth status` on older gh ([gh auth status](https://cli.github.com/manual/gh_auth_status): with `--json` exit is 0 regardless) | `auth logout` |
| `gcloud` | `gcloud` | `CLOUDSDK_CONFIG` | `auth login` | `auth list --format=json` | `auth revoke --all` |
| `azure` | `az` | `AZURE_CONFIG_DIR` | `login` | `account show --output json` | `logout` |
| `aws` | `aws` | `AWS_CONFIG_FILE`, `AWS_SHARED_CREDENTIALS_FILE` | `configure` | `configure list` (offline; no network call) | none |

- For Codex the core writes `cli_auth_credentials_store = "file"` into
  `<tools/codex>/config.toml` if the file does not exist, so the login stays in the profile
  directory ([Codex auth](https://learn.chatgpt.com/docs/auth.md)). An existing file is never rewritten.
- Claude: status `SignedIn` requires exit 0; the label is the email/organisation from the
  JSON when present. If `configDirectory` is present and differs from the profile's
  directory, or `authMethod` is not `claude.ai`, status is `SignedIn` with a `warning`
  (`docs/PLAN.md` §6.5, §6.8). Unknown JSON fields are ignored; unparseable output yields
  `Unknown` with the first line of output, never a crash.
- **Status values:** `not_installed | signed_out | signed_in { account, warning? } |
  unknown { message }`. Cached per profile and tool in `profile.db` with `checked_at`.
- **Custom tools** (app scope, stored in `app.db`): the user supplies name, binary, one
  config variable, and argv arrays for login, status and logout. `status_parser` is
  `exit_code`. `isolation` is `unverified`.

**Environment allowlist** (`docs/PLAN.md` §6.6). The environment for every status command,
terminal and MCP probe is *built*, not filtered: `PATH` (resolved, see below), `HOME`,
`USER`, `LOGNAME`, `SHELL`, `TMPDIR`, `LANG`, `LC_*`, `TERM`, proxy variables
(`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `ALL_PROXY` in both cases), `SSL_CERT_FILE`,
`SSL_CERT_DIR`, the Windows equivalents (`USERPROFILE`, `APPDATA`, `LOCALAPPDATA`,
`SystemRoot`, `ComSpec`, `PATHEXT`, `TEMP`, `TMP`), plus the config variables of the
selected tools. Nothing else passes, so `ANTHROPIC_API_KEY`, `GH_TOKEN`,
`CLAUDE_CODE_OAUTH_TOKEN` and similar cannot override a profile login
([authentication precedence](https://code.claude.com/docs/en/authentication)). This is a
pure function with table-driven tests.

**PATH resolution.** A macOS app started from Finder does not inherit the shell's `PATH`
`[no source: common convention]`, so Homebrew and npm-installed CLIs would look "not
installed". On Unix the core asks the user's login shell once at startup
(`$SHELL -ilc 'printf "__VISION_PATH__%s__END__" "$PATH"'`, 5 s timeout, output parsed
between the markers) and appends well-known directories that exist
(`/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`, `~/.cargo/bin`, `~/.npm-global/bin`,
`~/.claude/local`, `~/google-cloud-sdk/bin`). Failure falls back to the process `PATH` plus
those directories. Binaries are resolved to absolute paths against this `PATH` before spawn.

**Terminal launch** (`docs/PLAN.md` §6.5: sign-in happens in the system terminal so codes
never pass through Vision). The core writes a launch script into
`<data root>/tmp/` (mode 0700, removed on next start) that exports the allowlisted profile
variables, prints which profile and tool it is for, runs the argv with every argument
shell-quoted by a tested quoting function, and keeps the window open.
macOS: `open -a Terminal <script>.command`; Linux: first available of
`x-terminal-emulator`, `gnome-terminal`, `konsole`, `xterm`; Windows: a `.cmd` file via
`cmd /c start`. The script contains directory paths only, never a secret.

`profile_open_terminal` opens a shell with every tool's variables for that profile, so
`claude`, `gh`, `gcloud` in that window use the profile's accounts.

### 2.5 MCP servers (M10, profile scope)

```
McpServer {
  id, name,                      // name: ^[a-zA-Z0-9_-]{1,64}$, unique per profile
  transport: stdio | http,
  command, args[],               // stdio
  url,                           // http: https:// only, or http:// for localhost/127.0.0.1/[::1]
  env:     [{ key, value | secret }],   // stdio
  headers: [{ key, value | secret }],   // http
  tool_ids[],                    // which profile tool logins the server's environment gets
  enabled,
  health: { status: untested|ok|needs_auth|error, message?, tools: [{name, description}],
            server_name?, server_version?, checked_at? }
}
```

- **Secrets.** A value marked secret is stored in the OS credential store through the
  `SecretStore` trait (service `io.github.jakubkodajek.vision`, account
  `mcp/<profile-id>/<server-id>/<env|header>/<key>`); the database keeps only the reference.
  The UI never receives a secret value back, only `has_value: true`. Deleting a server or a
  profile deletes its secrets. If no credential store is available the save fails with
  `ErrorCode::SecretStoreUnavailable` instead of writing plaintext. These are MCP server
  secrets supplied by the user, not AI or GitHub tokens (ADR-0004 unchanged).
- **Test (health check).** stdio: spawn the command with the allowlisted profile
  environment plus the server's env, perform MCP `initialize`, `notifications/initialized`
  and `tools/list` over newline-delimited JSON-RPC, 20 s overall timeout, then terminate the
  whole process group. http: Streamable HTTP `initialize` + `tools/list` (JSON or SSE
  response); HTTP 401/403 maps to `needs_auth`
  ([MCP specification, transports](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)).
  The official Rust SDK (`rmcp`) is used behind `McpProbe` if a stable (non-beta) release
  covers both transports; otherwise a minimal client is written against the specification
  (`docs/PLAN.md` §3.6, R7). The choice and its reason are recorded in `memory/decisions.md`.
  Responses are size-capped (1 MiB) and tool descriptions are treated as untrusted text.
- **Claude Code config.** `mcp_render_claude_config(profile)` is a pure function producing
  the `{"mcpServers": {...}}` document Claude Code accepts (stdio entry `command/args/env`,
  http entry `type: "http", url, headers`: [Claude Code MCP](https://code.claude.com/docs/en/mcp.md)).
  It is what F-020 will write as the per-run `--mcp-config` file. Until runs exist,
  **Sync to Claude Code** applies it to the profile's user scope by running
  `claude mcp remove --scope user <name>` then `claude mcp add-json --scope user <name> <json>`
  with the profile environment, only for servers Vision manages (tracked by name in
  `profile.db`). Because Claude Code stores env values in its own config, the UI states that
  secret values are written into that profile's Claude Code configuration.
- **Authorize** (http servers needing OAuth): opens the system terminal with
  `claude mcp login <name>` under the profile environment
  ([CLI reference](https://code.claude.com/docs/en/cli-reference.md)); tokens stay in the CLI.

### 2.6 IPC contract (F-004)

TypeScript types are generated from the Rust types (`ts-rs`, exported by a test into
`src/ipc/bindings.ts`); `make lint` fails when the committed file is stale. A hand-written
`src/ipc/client.ts` wraps `invoke` with one typed function per command and validates
nothing twice (types come from Rust). Every command returns `Result<T, IpcError>`.

```
IpcError { code: ErrorCode, message: string }   // message is safe to show; no paths to secrets
ErrorCode = invalid_input | not_found | conflict | not_installed | timeout | io
          | schema_too_new | secret_store_unavailable | terminal_unavailable | internal
```

| Command | Arguments | Returns |
| --- | --- | --- |
| `app_info` | | `AppInfo { name, version }` |
| `bootstrap` | | `Bootstrap { profiles, active_profile_id, platform }` |
| `profile_create` | `{ name, kind, accent }` | `Profile` |
| `profile_update` | `{ id, name?, kind?, accent? }` | `Profile` |
| `profile_delete` | `{ id, confirm_name }` | `null` |
| `profile_set_active` | `{ id }` | `null` |
| `profile_open_terminal` | `{ profile_id }` | `null` |
| `tools_list` | `{ profile_id }` | `ToolView[]` (spec + cached status + version, no process spawn) |
| `tool_check` | `{ profile_id, tool_id }` | `ToolView` (detects binary, runs status) |
| `tool_sign_in` | `{ profile_id, tool_id }` | `null` (terminal opened) |
| `tool_sign_out` | `{ profile_id, tool_id }` | `null` (terminal opened) |
| `tool_open_install_page` | `{ tool_id }` | `null` (opens the registry's `install_url`) |
| `custom_tool_save` | `{ tool: CustomToolInput }` | `ToolSpecView` |
| `custom_tool_delete` | `{ tool_id }` | `null` |
| `mcp_list` | `{ profile_id }` | `McpServerView[]` |
| `mcp_save` | `{ profile_id, server: McpServerInput }` | `McpServerView` |
| `mcp_delete` | `{ profile_id, server_id }` | `null` |
| `mcp_test` | `{ profile_id, server_id }` | `McpServerView` |
| `mcp_sync_claude` | `{ profile_id }` | `SyncReport { synced[], removed[], failed[{name,message}] }` |
| `mcp_authorize` | `{ profile_id, server_id }` | `null` (terminal opened) |

The capability file lists exactly these commands. The CSP stays as it is.

## 3. UI

- **First run:** no profiles → a welcome screen that creates the first profile (name, kind,
  accent) and then lands on Tools.
- **Sidebar:** real profiles in the switcher with "New profile…" and "Manage profiles";
  navigation gains **Tools** and **MCP servers**.
- **Tools:** one card per tool: name, status badge (text + icon, not colour alone), account
  label, version, isolation note, buttons Sign in / Sign out / Check again / Install
  (opens the official page). After Sign in the card shows "Waiting for sign-in in the
  terminal…" and re-checks every 3 s for up to 10 min, or until the user cancels. Statuses
  are checked on first visit per profile and on demand, not on a timer.
- **MCP servers:** list with transport, health badge, tool count; add/edit dialog (stdio or
  HTTP, env/headers with a "secret" toggle that never shows stored values, tool logins to
  share); Test, Authorize, Delete (confirm); "Sync to Claude Code" with a result summary.
- **Settings:** profile management (rename, kind, accent, delete with typed confirmation),
  appearance, about.
- **Home:** an overview of the active profile (tool sign-in summary, MCP servers, next
  steps). Projects, Agents, Tasks, Knowledge stay as labelled "not available yet" sections;
  demo conversation data is no longer shown in the app (components stay, covered by tests).
- Every view has loading, empty and error states; all controls keyboard operable; WCAG 2.2 AA
  (`.claude/rules/frontend.md`). No inline styles (CSP `style-src 'self'`).

## 4. Installers (F-002)

- `bundle.macOS.signingIdentity: "-"` (ad-hoc): Apple Silicon requires a signature for apps
  from the internet; ad-hoc signing still needs the user to allow the app in Privacy &
  Security ([Tauri macOS signing](https://v2.tauri.app/distribute/sign/macos/)). The README
  documents the first-launch steps.
- `bundle.macOS.dmg`: custom background with a drag arrow, window size, app and
  Applications positions ([Tauri DMG](https://v2.tauri.app/distribute/dmg/)). The page notes
  that icon positions are not applied on CI runners (tauri-apps/tauri#1731); the build
  workflow must produce a correct layout anyway or the limitation is recorded.
- `bundle.macOS.minimumSystemVersion`, real icons generated from one SVG source, category,
  copyright, short and long description.
- `.github/workflows/build.yml`: matrix macos-latest (aarch64 and x86_64 targets),
  windows-latest, ubuntu-latest; runs `make check`, `tauri build`, uploads installers as
  artifacts on pull requests and `main`; on a `v*` tag creates a draft GitHub Release with
  the installers and SHA-256 checksums. Third-party actions pinned to commit SHAs; minimal
  `permissions`.

## 5. Acceptance criteria

Storage and profiles
- AC1 Fresh data root: `bootstrap` returns no profiles; after `profile_create`, a restart
  (new `Core` on the same directory) returns it.
- AC2 Migration from an older fixture database creates a backup first; a database with a
  newer `user_version` is refused with `schema_too_new` and is byte-identical afterwards.
- AC3 Profile directories are mode 0700 on Unix; names are validated; duplicate names
  conflict; delete with a wrong confirmation changes nothing; delete removes the directory
  and the profile's secrets.

Tools
- AC4 The environment builder passes only allowlisted variables: with `ANTHROPIC_API_KEY`,
  `GH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` in the parent, none reaches a status command, a
  terminal script or an MCP probe (tested with a fake CLI that dumps its environment).
- AC5 Each preset's status parser has fixtures for signed in, signed out, garbage output,
  and a timeout; `not_installed` when the binary is absent; two profiles get different
  config directories and independent statuses.
- AC6 Sign-in writes a launch script whose content is asserted (exports, quoted argv, no
  parent secrets) and calls the launcher; arguments containing quotes, spaces, `$`, backticks
  and newlines cannot break out of quoting (property-style test).
- AC7 Custom tools: invalid ids, binaries with path separators or shell metacharacters, and
  non-https install URLs are rejected.

MCP
- AC8 CRUD with validation (name pattern, URL scheme rule, duplicate names); secrets never
  appear in any IPC response or in `profile.db` (asserted by scanning both).
- AC9 `mcp_test` against a fake stdio MCP server binary returns its tools; a server that
  never answers times out in under 25 s and leaves no child process; a server that prints
  garbage or a 5 MiB line yields `error`, not a crash; HTTP 401 yields `needs_auth`
  (local test server).
- AC10 `mcp_render_claude_config` output matches golden files for stdio and http; sync
  invokes the expected `claude mcp` argv with the profile environment (fake runner).

IPC and UI
- AC11 `src/ipc/bindings.ts` is generated and `make lint` fails when stale; the capability
  file lists exactly the commands in §2.6.
- AC12 UI tests (vitest, mocked IPC) cover: first-run profile creation, switching profiles
  shows only that profile's tools and servers, sign-in polling reaches "Signed in as …",
  error states for every command, MCP add/edit/test/delete, secret fields never render a
  stored value, typed-confirmation delete. axe reports no serious violations on Tools, MCP
  and Settings in light and dark.

Installers
- AC13 The build workflow is valid, pins actions by SHA, and on this PR produces a `.dmg`
  for Apple Silicon as an artifact; `tests/config` asserts the bundle settings in §4.

Whole
- AC14 `make check` exits 0; no existing test is deleted, skipped or loosened without a
  note in the PR.

## 6. Risks

| Risk | Mitigation |
| --- | --- |
| CLI output formats change | Defensive parsers with `unknown` state and fixtures; presets are data |
| gh keyring not separated by config dir | `--insecure-storage` so the token stays in the profile directory (`docs/PLAN.md` §6.4) |
| A compromised webview adds a custom tool or stdio MCP server to run a binary | Strict CSP, no remote content, argv arrays (no shell), binary validation; inherent to a product that runs user-configured tools, recorded as residual risk |
| Unsigned (ad-hoc) macOS build needs a manual first-launch approval | Documented in README; Developer ID signing is a later owner decision (`docs/PLAN.md` Q10) |
| gcloud/azure/aws isolation unverified on a real machine | Marked `unverified` in the registry until F-013 |
